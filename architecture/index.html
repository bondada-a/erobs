Architecture

EROBS coordinates robot motion, tool changes, and vision from an ordered JSON task script. The orchestrator manages the sequence; task stages build motion plans; MoveIt and device drivers carry them out.

The platform uses ROS 2 Jazzy, MoveIt 2, and MoveIt Task Constructor (MTC). The operator GUI communicates with the runtime through ROS actions, services, and topics.

From task script to execution

  1. Submit. The GUI or another client sends the script to /beambot_execution.

  2. Prepare. The orchestrator validates the script, resolves named poses, and prepares MoveIt for the selected tool.

  3. Plan and execute. Compatible MoveTo and end-effector steps share an MTC task. Other operations run through their task servers or orchestrator helpers. Vision tasks first turn camera measurements into motion targets.

  4. Report. The orchestrator publishes progress and returns a result to the client. Pause and cancellation take effect at execution boundaries; see execution controls.

Process boundaries

The orchestrator owns MoveIt startup. It starts the robot stack when a task needs it and manages model changes during tool exchange. See MoveIt lifecycle.

Task servers run separately. Most use BaseActionServer to accept one goal at a time. The sample server shares that limit across its pick and place endpoints. Batched MoveTo and end-effector stages run inside the orchestrator process instead of sending child action goals.

Caches belong to their owning process. The vision-scan and unified vision-task servers keep separate marker caches. A scan result is not automatically available to a later unified vision task.

Vision and pipettor servers are optional launch groups. Mapping uses the separate octomap_mapping.launch.py launch file. See configuration and deployment boundaries for how these components are enabled.
